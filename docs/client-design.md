# Client design

A Ratatui terminal application (`client` workspace crate) that manages multiple
container servers and their instances over the existing bierpc API.

Decisions already made (2026-07-18):

- **Terminals**: *not* a TUI screen. They are their own CLI subcommands —
  `client shell <target>` and `client attach <target>` — run in a separate
  console. `shell` runs against a **real PTY** and behaves like PuTTY or ssh:
  full-screen programs work, every key including `Ctrl+C` goes through, and
  `exit` ends it. `attach` stays pipe-based and line-oriented, because the
  supervised process it bridges to is. (Revised twice on 2026-07-18: first
  moving terminals out of the TUI, then making `shell` a real terminal.)
- **Navigation**: single screen at a time, push/pop with `Esc` — no tab bar.
- **Wire types**: extracted into a shared `protocol` crate.
- **File transfer**: remote file browser (requires a small server API addition).
- **Auth**: a pre-shared 1024-byte key, generated by `keygen` on both sides.
  Every request and reply is HMAC-signed. See §8.

## 1. Workspace changes

### 1.1 New crate: `protocol`

Move the wire types out of `server` so the client does not pull gix,
processkit, or sysinfo:

| From | Types |
|---|---|
| `server/src/api.rs` | `ErrorCode`, `ApiError`, `TerminalMode`, `Action`, `Response` |
| `server/src/manager.rs` | `RetryPolicy`, `RunState`, `RepoState`, `GroupStats`, `InstanceStatus`, `InstanceStatResponse` |
| `server/src/storage.rs` | `InstanceConfig` |

Stays in `server`: `State` (holds processkit's `Outcome`), the
`From<&State> for RunState` impl (legal under the orphan rule — `&State` is
fundamental, hence local), `ServerStg`, `InstancePatch` (server-internal, not
a wire type), and all handler logic. `should_restart` becomes a free function
in `manager.rs`: it needs `Outcome`, and an inherent method on a now-foreign
`RetryPolicy` would be illegal.

`server::api` and `server::manager` re-export the moved types
(`pub use protocol::…`), so existing `server::…` paths keep working.

`protocol` needs a `tokio` dependency (`io-util`): `bier_derive`'s generated
code refers to `tokio` paths directly.

The bierpc turbofish quirk (generic field types in *named* enum variants must
be written `Vec::<u8>`) applies to everything in this crate — the existing
NOTE comment moves along with the types.

**Status: done.** `smoke` passes unchanged (full flow + phase2).

### 1.2 New crate: `client`

Dependencies: `protocol`, `bierpc`, `ratatui`, `crossterm`, `tokio`,
`futures`, `clap`/`clap_derive`, `dirs` (config location), `anyhow`.

### 1.3 Server API additions for the file browser — **done in M0**

Landed with the extraction so the wire format would not have to change again:

```rust
Action::ListDir { path: PathBuf }
Response::DirListing { path: PathBuf, entries: Vec::<DirEntry> }
struct DirEntry { name: String, is_dir: bool, size: u64, modified_secs: Option<u64> }
```

- `ListDir` resolves through the existing `transfer::resolve_path` jail
  (file_roots + instances dir, `..` rejected), so the browser can only see
  what transfers can already touch. Entries that cannot be stat'd are skipped
  rather than failing the listing; dirs sort first, then names, case-folded.
- `InstanceStatus` gained `repo_dir: PathBuf` so the client can root the
  browser at the instance's repo without hardcoding the server's storage
  layout. The absolute path round-trips through `resolve_path` because it
  lives under the instances dir (verified in `smoke`).
- Browsing the wider `file_roots` is a possible later extension (would need
  the roots exposed, e.g. in `Stat`); v1 roots the browser at the repo dir.

Note: `Response::DirListing` was inserted before `Error`, shifting variant
indices. Client and server must be built from the same revision — on-disk
formats (`ServerStg`, the instance index) are unaffected.

## 2. Client-local storage

The client keeps a *book*, bierpc-serialized (consistent with the server's
`.chld` files) at `%APPDATA%\container-client\servers.chld`, overridable with
`-c <path>`:

```rust
struct Book { key: Vec<u8>, servers: Vec<ServerEntry> }
struct ServerEntry { id: u128, name: String, addr: SocketAddr, key: Vec<u8> }
```

`ServerEntry::key` is empty in the common case and the book-level `key` is
used; a per-server key overrides it, so a fleet can share one passphrase while
one machine keeps its own. `Book::key_for` resolves that precedence once, and
`Endpoint { addr, key }` carries the pair together from there on — no call
site can accidentally talk to one server with another's key.

Servers are managed entirely in-app (add / edit / remove on the landing page);
keys are set by `client keygen`. Hand-editability is not a requirement.

Nothing about instances is stored client-side — instances are always fetched
live from their server.

## 3. Architecture

### 3.1 Event loop

Single tokio task owns the terminal and the `App` state. It `select!`s over:

- crossterm `EventStream` (keys, resize),
- a tick interval (~250 ms) for redraws/spinners,
- an `mpsc::Receiver<AppEvent>` fed by background tasks.

```rust
enum AppEvent {
    Snapshot { server: usize, result: Result<StatData, String> },   // poller
    Detail   { server: usize, id: u128, result: Result<InstanceStatus, String> },
    ActionDone { desc: String, result: Result<(), String> },        // run/stop/…
    Listing  { …result of ListDir… },
    TransferProgress { done: u64, total: Option<u64> },
    TransferDone { result: Result<(), String> },
    TerminalReady(TcpStream),   // handshake finished, switch to passthrough
}
```

The UI never awaits an RPC directly; every user action spawns a task that
posts an `AppEvent` back. The loop stays responsive even with unreachable
servers.

### 3.2 Networking (`net.rs`)

- bierpc is one-shot: **a fresh `RpcClient` per call** (server closes the
  connection after each response). One helper:
  `async fn call(addr: SocketAddr, action: Action) -> Result<Response, NetError>`
  with a connect+call timeout (~5 s), plus thin typed wrappers that map
  `Response::Error(ApiError)` into `NetError::Api`.
- **Pollers**: one background task per server entry, sending `Action::Stat`
  every 2 s and posting `AppEvent::Snapshot`. The manage screen additionally
  polls `CheckInstance` for the focused instance each cycle (full config +
  group stats).
- **Network rates**: `Stat`'s recv/trans counters are turned into B/s
  client-side from the delta between consecutive snapshots. A counter that
  goes backwards (server restart) yields a 0 rate, never a spike.

  Building this exposed three bugs in the server's `Stat`, fixed in M1
  (`server/src/api.rs`, asserted in `smoke`):

  | Was | Effect | Now |
  |---|---|---|
  | `System::new_all()` per call | CPU always ~100%: sysinfo derives usage from two refreshes, and a fresh `System` has one | a persistent `System`, refreshed per call |
  | `NetworkData::received()` | always ~0: that is bytes since the *last refresh*, and the list was created that instant | `total_received()` (cumulative) |
  | `free_memory()` | understates what is usable on Linux | `available_memory()` (identical on Windows) |

  The persistent `System` also stops `stat` from walking the whole process
  table on every poll. The very first `Stat` after boot still reports a CPU
  figure from a single sample; it is correct from the second poll on.
- **Session channel** (terminals & transfers): a persistent call on the same
  mutually-authenticated connection (`protocol::session`), opened after reading
  the server's `SessionStart`.

### 3.3 State model

```rust
struct App {
    servers:   Vec<ServerEntry>,
    snapshots: Vec<Option<Snapshot>>,        // parallel to servers
    screens:   Vec<Screen>,                  // stack; last = active, Esc pops
    modal:     Option<Modal>,                // overlay on the active screen
    status:    Option<Toast>,                // one-line feedback, auto-expires
}

enum Screen {
    Landing     { cursor: usize },           // flattened tree cursor
    Manage      { server: usize, id: u128 },
    FileBrowser { server: usize, id: u128, path: PathBuf, entries: Vec<DirEntry>, cursor: usize },
}

enum Modal {
    AddServer(Form), EditServer(Form),
    CreateInstance(Form), EditInstance(Form),
    Confirm { message: String, on_yes: PendingAction },
    Prompt  { message: String, input: String, on_submit: PendingAction }, // file paths
    Transfer { desc: String, done: u64, total: Option<u64> },
    Help,
}
```

`Snapshot` = vitals + `HashMap<u128, InstanceStatResponse>` + `last_seen`
+ computed network rates, or an error string for unreachable servers.

## 4. Screens

### 4.1 Landing page

```
 container client                                      2 servers · ? help · q quit
──────────────────────────────────────────────────────────────────────────────────
 ▸ ● home-box        127.0.0.1:5000    cpu 12%  ram 3.1/16G
     ▶ instance 01        running (pid 4312)
     ■ instance 02        stopped
 ▸ ✗ vps             10.0.0.7:5000     unreachable · last seen 14:02:11
──────────────────────────────────────────────────────────────────────────────────
 [enter] manage  [a]dd server  [n]ew instance  [e]dit  [d]elete  [r]efresh
```

- One flattened tree: server rows with inline vitals summary, instance rows
  nested beneath (from that server's latest snapshot).
- Instance glyphs: `▶` running · `↻` starting/backoff · `■` stopped or
  exited 0 · `✗` failed / exited non-zero / clone failed · `⋯` provisioning.
- Keys: `↑/↓` move, `Enter` on an instance → Manage; `Enter`/`Space` on a
  server → collapse/expand; `a` add server (name + addr form; the address is
  validated but *not* pinged before saving — a server that happens to be down
  must still be addable, and the poller reports reachability within 2s
  anyway); `n` create instance on the selected server;
  `e` edit / `d` remove the selected entry (server removal is local only and
  confirmed; instance removal calls `RemoveInstance` with a "delete files?"
  toggle in the confirm dialog); `r` force an immediate poll; `q` quit.

### 4.2 Manage screen

```
 container   smoke-box / tui-smoke
╭ smoke-box ─────────────────╮╭ tui-smoke ──────────────────────────────────────╮
│cpu  ▓░░░░░░░ 8%            ││repo      https://…/Hello-World (default branch) │
│ram  ▓▓▓▓░░░░ 14G/32G       ││checkout  ready                                  │
│dsk  ▓▓▓▓░░░░ 1.8T/3.6T     ││command   cmd.exe /q /k "echo started"           │
│net  ↓368B/s ↑326B/s        ││state     ▶ running                              │
│                            ││pids      20864                                  │
╰────────────────────────────╯│usage     2 processes · cpu 0.4s · peak 7.5M     │
╭ instances ─────────────────╮│policy    never restart · autostart off          │
│ ▶ tui-smoke                ││                                                 │
│ ■ other-thing              ││terminals — run in another console               │
│                            ││  client shell smoke-box/tui-smoke    new shell  │
│                            ││  client attach smoke-box/tui-smoke   the process│
╰────────────────────────────╯╰─────────────────────────────────────────────────╯
 ↑↓ instance  r start  x stop  k kill  u update repo  e edit  n new  D remove
```

- Left sidebar: the server's vitals and its instance list. `↑/↓` or `[`/`]`
  switches instance without leaving the screen; the detail pane reloads.
- Vitals are drawn as text meters rather than `Gauge` widgets so the label,
  bar and figure fit on one line at sidebar width. They turn yellow past 75%
  and red past 90%.
- Main pane: full `InstanceStatus` — config, repo state, run state (pids,
  restarts, exit code/signal, backoff countdown), `GroupStats`. The checkout
  path goes last: it is the one field long enough to wrap, and wrapping there
  cannot push anything more useful down the pane.
- Since terminals are a CLI mode, the pane's job is to hand over the exact
  command to paste rather than to open one.
- Below the detail pane, the **console** shows the instance's captured
  stdout/stderr — see §4.4. It gets whatever height is left, being the part
  you actually sit and watch.
- Actions (all async, feedback via toast): `r` run · `x` stop · `k` kill
  (confirm) · `u` update repo · `e` edit config · `n` new instance ·
  `D` remove (confirm + delete-files toggle, then pop back to landing) ·
  `Esc` back.
- Detail refreshes on the same 2s cadence as the poll: a `Snapshot` for the
  managed server triggers a `CheckInstance`. A reply for an instance the user
  has since navigated away from is dropped rather than shown.
- If the managed instance disappears from the server (removed elsewhere), the
  screen pops back to the landing page rather than describing something gone.
- Create/edit instance form fields: name, repo url, branch (blank = default),
  command, args (space-split, `"quotes"` group), env (`KEY=VALUE;` separated
  on one line), autostart toggle, retry policy picker
  (`Never/OnCrash/Always/Retry`) plus a retry-limit field. Editing pre-fills
  from the live `InstanceStatus` and sends every field — the server treats
  `None` as "unchanged", and the form always carries the whole config.

### 4.3 Terminals — a CLI mode, not a screen

```
client shell <target>     a fresh shell in the instance's checkout (docker exec)
client attach <target>    the running instance's stdin/stdout   (docker attach)
```

Keeping these out of the TUI means the app never suspends or restores itself,
and a session owns the console outright. The manage screen's job is to show
the exact command for the instance you are looking at.

**Targets** (`client/src/target.rs`) accept `server/instance`, or a bare
`instance` searched across every server in the book. A bare name matching on
two servers is an error listing both, never a silent pick. Instance ids
(32-hex) work anywhere a name does. When searching, an unreachable server is
skipped and mentioned in the error rather than aborting the lookup — one
server being down should not stop you attaching to another.

**Flow**: `net::session(Session::Shell/Attach, …)` opens a persistent call on a
fresh mutually-authenticated connection, reads the server's `SessionStart`, and
runs the pump over the same stream (`protocol::session`, `§8`). No separate
port or token — mTLS authenticates the caller.

The two modes differ because what is on the far end differs.

#### `shell` — a real terminal

The server opens a **PTY** (ConPTY on Windows) via `portable-pty` and spawns
the shell into it; processkit is pipe-only and is not used on this path. The
shell then does its own echoing, line editing and screen drawing, so this end
is a dumb conduit and full-screen programs work.

- **`Ctrl+C` reaches the remote shell and interrupts the running command**,
  exactly as in PuTTY. The session ends when the shell does — type `exit`.
  There is no client-side escape key.
- **Framing** (`protocol::term`): `[u8 kind][u32 be len][payload]` in *both*
  directions now (Data, Resize, Close). The shared connection is reused for the
  call's reply, so it can never be closed to mean "done" — instead each side
  sends `Close` and drains to the peer's `Close` before the reply is read.
  Unknown frame kinds are skipped rather than treated as a desync, so the
  format can grow.
- **Input is platform-split, because "raw bytes in" does not mean the same
  thing on both OSes** (`client/src/terminal.rs`, `pump_shell`):
  - **Unix**: a raw-mode tty hands over exactly what a terminal produces —
    arrows, Ctrl+C, everything — as a byte stream, so those bytes are
    forwarded verbatim from a dedicated OS thread (a tty read blocks and
    can't be cancelled, so it can't live on the async task that owns the
    session). Resize has no event on this path and is polled every 250ms.
  - **Windows**: a console *byte* read only ever yields character keys —
    arrows, function keys and Ctrl+C never appear in the stream no matter
    which console modes are set. (Verified directly: `client/examples/
    evt_probe.rs` reads the same keystrokes three ways — crossterm events,
    `ReadConsoleA`, `ReadConsoleW` — under a real ConPTY, and only the event
    API sees the Up arrow or the Ctrl+C at all.) So Windows instead reads
    decoded `crossterm::event::Event`s, the same API the TUI uses, and
    `encode_key` turns each one back into the xterm byte sequence a terminal
    would have sent (`\e[A` for Up, `\e[1;5C` for Ctrl+Right, C0 codes for
    Ctrl+letter, ESC-prefixed for Alt+key, `\e[15~`-style for function keys).
    ConPTY on the far end parses that back into key events for the shell.
    `KeyEventKind::Release` is dropped — Windows raises one for every
    keypress and forwarding it would double every character — except a
    release that arrives with no matching press on record, which does
    happen (a `Ctrl+C` synthesized from certain input can show up
    release-only) and must not be dropped or the keystroke is lost.
    Resize arrives as `Event::Resize`, no polling needed.
- **Console modes** (`client/src/console.rs`): `crossterm::enable_raw_mode` is
  *not* sufficient on Windows — it only clears the line/echo/processed-input
  bits. Windows input is read as events regardless (see above), so the input
  side just needs echo/line-editing/Ctrl+C-as-signal off; the client clears
  `ENABLE_ECHO_INPUT | ENABLE_LINE_INPUT | ENABLE_PROCESSED_INPUT`. Output
  gets `ENABLE_VIRTUAL_TERMINAL_PROCESSING | DISABLE_NEWLINE_AUTO_RETURN` so
  the remote's escape sequences render and a full-width line doesn't
  double-space. Both are restored exactly as found via a `Drop` guard, and
  each half is optional — a redirected stdin or stdout is skipped rather than
  failing, so a scripted `client shell` still works.
- **Windows output filtering**: ConPTY addresses two things *at the
  terminal* rather than at the screen, and both have to be intercepted
  before they reach the local console — `OutputFilter` in `terminal.rs`
  strips them out of the byte stream and answers on the socket itself:
  - `\e[6n` (cursor position report): ConPTY blocks its entire output
    pipeline waiting for a reply. The client answers with the *local*
    console's real cursor position (`console::cursor_position`, via
    `GetConsoleScreenBufferInfo`), after flushing everything received before
    the query so the position is accurate. Letting this reach the local
    console instead would have Windows inject the reply into *our own* input
    queue, where it decodes as garbage — an early version of this code
    showed a `\e[18;1R` reply from the console arriving back as a phantom
    `F3` keypress.
  - `\e[?9001h` / `\e[?9001l`: ConPTY's own request to switch its terminal
    into win32-input-mode. The client already sends ConPTY plain VT and
    never wants that switch applied to the *local* console, so these are
    dropped with no reply.
- **Flushing**: every session write flushes the buffered stream immediately —
  a keystroke and its echo are single-digit-byte writes, and leaving them in
  bierpc's `BufStream` until the next larger write looks exactly like typing
  lag. (The old dedicated socket used `TCP_NODELAY` for the same reason.)
- **Teardown**: ConPTY holds its end of the output pipe open until the
  pseudoconsole is closed, so the reader thread does *not* see EOF when the
  shell exits. A separate thread waits on the child and signals the session
  to close; without it, typing `exit` would hang. The select is `biased` so
  pending output is flushed before the exit branch wins the race. On the
  client, keystrokes are likewise read on a plain OS thread rather than
  `tokio::io::stdin()` — a blocked console/tty read can't be cancelled, and a
  tokio blocking task stuck in one keeps the whole process alive after the
  session ends, until one more key is pressed. A detached thread just dies
  with the process.
- **`SetConsoleCtrlHandler(None, 0)`** is called at the top of both `client`
  and `server` `main()`. Windows processes can inherit an "ignore Ctrl+C"
  flag from whatever launched them (a script, a service wrapper); if the
  *server* inherited it, every shell it spawns into a pty inherits it too,
  and Ctrl+C would silently do nothing no matter what the client sent —
  confirmed directly with `evt_probe ping-test`, which showed a bare `0x03`
  and even a synthesized win32-input-mode Ctrl+C both failing to interrupt a
  running `ping` until this flag was cleared. Clearing it up front restores
  normal behavior regardless of how either process was launched.
- **Diagnostics**: `CONTAINER_SHELL_TEE=<path>` writes every byte the server
  sent (pre-filtering) to a file, and `CONTAINER_SHELL_DEBUG=<path>` logs
  every key/resize/socket event the pump handles — for reproducing "the
  terminal shows garbage" reports without guessing.

#### `attach` — unchanged, and line-oriented

The supervised process runs on pipes with no PTY, so nothing echoes and no
escape sequence means anything. This end keeps its small line editor (local
echo, Backspace, `\r\n` on Enter) and **`Ctrl+C` ends the session** rather
than being forwarded — there is nothing on the far side that could act on it.
Detaching leaves the instance running, asserted in `tui_smoke`.

Giving `attach` a PTY too would mean running instances under one, which would
push ANSI escapes into the console ring buffer (§4.4) and the supervisor's
restart handling. Deliberately not done.

### 4.4 Console output

```
╭ console ─────────────────────────────────────────────────────────╮
│16:49:39 ── started ──                                            │
│16:49:39 instance-started                                         │
│16:49:40 C:\…\repo>                                               │
╰──────────────────────────────────────────────────────────────────╯
```

Server side (`manager.rs`): each instance owns a bounded ring buffer of 1000
`ConsoleLine { at_ms, stream, text }`, filled from the same supervise loop
that feeds attached terminals — but **unconditionally**, where the terminal
broadcast is skipped when `receiver_count() == 0`. The console must hold what
happened with nobody watching; that is the whole point.

- The buffer lives on `ManagedInstance`, not on `Service`, so it **survives
  restarts**: the output explaining why something crashed is written before
  the restart, not after.
- The supervisor writes its own marker lines (`── started ──`,
  `── exited: Exited(1) ──`, `── restarted (attempt 3) ──`), so a restart loop
  is legible in the scrollback rather than an unexplained repeat.
- `Action::TailConsole { id, lines }` → `Response::Console { lines, dropped }`.
  `dropped` counts what the client is *not* seeing — both evicted from the
  ring and trimmed by the requested tail — so the panel can say "… N earlier
  lines discarded" instead of implying the instance started mid-stream.

Client side: the tail is fetched alongside the detail, on the same 2s cadence.
Stderr renders red; timestamps are `hh:mm:ss` **UTC**, since they are the
server's stamps and a local-time conversion here would be a guess. `PageUp`/
`PageDown` scroll and `End` returns to following. While scrolled back, arriving
lines shift the scroll offset to hold position, so reading is not yanked around
by a chatty instance.

### 4.5 File browser (M4, needs the server additions from §1.3)

- Opens from Manage via `f`, rooted at `InstanceStatus.repo_dir`; every
  navigation issues a `ListDir` (dirs first, then files with sizes).
- The client tracks its own path stack — `..` never goes over the wire (the
  server rejects it); `Backspace` pops, stopping at the root.
- `Enter` descend · `d` download selected file (path prompt, default:
  client cwd + filename) · `u` upload (prompt for local file; dest = current
  remote dir + filename) · `r` refresh · `Esc` back to Manage.
- Transfers run as background tasks over the session channel
  (`[u64 BE length][bytes]`), reporting `TransferProgress` into a modal with
  a gauge (download size comes from `SessionStart.size`, upload size from
  the local file). Downloads write `<dest>.part` and rename on completion,
  mirroring the server. The persistent call's reply is the commit ack: a
  `Done` means the server received (and, for archives, unpacked) the bytes.

## 5. Error handling

- Every RPC failure (connect, timeout, `Response::Error`) becomes a toast in
  the status line with the `ErrorCode` — never a crash, never a blocked UI.
- Unreachable servers stay listed (dimmed, `✗`, last-seen time); their manage
  screens show the stale snapshot with an "unreachable" banner.
- Panic hook + `Drop` guard restore the terminal (leave alt screen, disable
  raw mode) so a crash never leaves the console broken — doubly important
  since passthrough deliberately toggles screen state.

## 6. Verification

The client is a library plus a thin `main`, so the UI can be driven without a
human at a terminal — `client/examples/tui_smoke.rs` renders the real widgets
to ratatui's `TestBackend` and feeds the real state machine synthetic key
events, against a **live server**. It asserts on the rendered text, so it
covers polling, form validation, persistence and layout together.

```
# one terminal — the last argument is the auth phrase both suites expect
cargo run -p server --example mkconfig -- 127.0.0.1:5099 cfg.chld stg smoke-test-passphrase
cargo run -p server -- -c cfg.chld start
# another
cargo run -p server --example smoke     -- 127.0.0.1:5099   # server API
cargo run -p client --example tui_smoke -- 127.0.0.1:5099   # client UI
```

`tui_smoke` covers the landing page, the manage screen and its lifecycle
actions, the instance forms, target resolution, and terminal sessions —
including that ending an attach session leaves the instance running. The two
suites share a server, so neither may assume it is the only thing on it:
`tui_smoke` locates its own fixture instance by name rather than by row index.

`smoke` additionally covers every auth rejection path — wrong key, replay,
tampered payload, stale timestamp, and a reply verified against the wrong
nonce — building the bad requests via `auth::request_mac` rather than
reimplementing HMAC, since duplicated crypto in a test drifts and then passes
for the wrong reason.

Shell sessions are covered too: that the pty runs commands and echoes them
(asserted on `set /a 21*2` → `42`, since a pty echoes the input, so matching
the command text would pass even if nothing ran), that a resize frame reaches
the pty (`mode con` afterwards reports 120 columns — matched on the number,
because that output is localized), and that `exit` closes the session.

ConPTY probes the terminal it thinks it is attached to with `ESC[6n` and waits
for an answer. A real console replies by itself; the socket-based drivers have
to emulate that, which `pty_read_until` does.

The local console half — key decoding, output filtering, resize, Ctrl+C —
looked untestable at first, since none of it runs unless stdin/stdout are a
real console. It turns out a ConPTY child *is* a real console, so two more
probes close the gap without a human at a terminal:

- **`client/examples/evt_probe.rs`**: no server involved. Spawns itself
  under a ConPTY three ways — reading `crossterm::event::EventStream`,
  `ReadConsoleA`, `ReadConsoleW` — and compares what each sees for the same
  injected keystrokes. This is what proved a console byte read *never*
  yields an arrow key or Ctrl+C, whatever the mode bits say — the reason
  `pump_shell` reads events on Windows instead of bytes. Its `ping-test` mode
  drives a bare `cmd.exe` under a ConPTY and tries three encodings of Ctrl+C
  against a running `ping`, which is what caught the inherited
  "ignore Ctrl+C" console flag (below).
- **`client/examples/shell_probe.rs`**: spawns the real `client.exe shell`
  under a ConPTY against a live server and drives it like a human would —
  typing one key at a time (and measuring echo latency), arrow-key history
  recall, non-ASCII input, resize, Ctrl+C against a running command, and
  `exit`. `CONTAINER_SHELL_TEE`/`CONTAINER_SHELL_DEBUG` (set automatically by
  the probe) capture the exact bytes the pump received and every event it
  acted on, so a failure shows *what* went wrong, not just *that* something
  did.

```
cargo run -p client --example evt_probe                                  # no server needed
cargo run -p client --example shell_probe -- 127.0.0.1:5099 target/debug/client.exe
```

This is how the Windows-specific rework in §4.3 was found and verified: the
byte-forwarding `pump_shell` that shipped first passed every automated test
because none of them ran on a real console, and only broke once someone
actually typed into it. `smoke` and `tui_smoke` drive sessions through
`net::session` directly (a manual frame reader in place of a TTY), so the
session/framing logic keeps coverage independent of the ConPTY probes.

Two things to know when working on this:

- `cargo build` fails with "Zugriff verweigert (os error 5)" while a built
  `server.exe` is running — Windows locks the running image.
- Do not round-trip source files through PowerShell's `Get-Content`/
  `Set-Content`: 5.1 reads as ANSI by default and silently mangles the box-
  drawing characters these files are full of.

`App::run` is generic over `Backend` and over the input `Stream` for this
reason; `main` supplies `DefaultTerminal` and crossterm's `EventStream`.

Stop the server before rebuilding, or build with a separate
`CARGO_TARGET_DIR`.

## 8. Authentication

Both ends hold the same 1024-byte key. `protocol::auth::hash_or_random`
derives it from a passphrase with Argon2id — memory-hard, so a weak phrase
costs a guesser 64 MiB and real time per attempt — emitting all 1024 bytes
directly, or draws it from OS entropy when no phrase is given. The cost
parameters, version and salt are pinned constants: both ends must derive the
identical key, so changing any of them re-pairs every phrase-derived key.

```
server -c cfg.chld keygen <phrase>      # or --key <hex>
client              keygen <phrase>      # or --key <hex>, or --server <name>
```

A phrase never crosses the network: both sides derive the identical key from
it locally. A *random* key has to be copied, so whichever side generates one
prints it as hex and the exact command to paste on the other side.

### Envelope

`RpcServer` is parameterised over `Request`/`Reply` rather than
`Action`/`Response`, so authentication wraps every exchange rather than being
something each handler has to remember:

```rust
struct Request { nonce: Vec<u8>, timestamp_ms: u64, mac: Vec<u8>, payload: Vec<u8> }
enum Reply { Signed { timestamp_ms, mac, payload }, Rejected(AuthFailure) }
```

- **HMAC-SHA256** over `nonce || timestamp || payload`, verified with
  `Mac::verify_slice` (constant time).
- The action travels as an **opaque blob**, decoded only after the MAC
  verifies. Untrusted bytes never reach the deserializer, and the MAC does not
  depend on the encoding being canonical — `HashMap` field order is not.
- **Replies are signed against the request's nonce**, so a reply cannot be
  lifted from one exchange and replayed into another.
- **Timestamp window** of 60s, plus a **replay guard** that remembers nonces
  for twice that. Verification order is shape → MAC → freshness → replay: a
  nonce is only worth burning once the request is known to be authentic.
- A rejection is vague on the wire and detailed in the server log. `Rejected`
  is inherently unsigned, so the client treats it as a hint for the operator,
  never as a basis for a security decision.

### Transport encryption

The whole channel runs over **mutual TLS 1.3**, anchored in the shared key
(`protocol::tls`): *both* ends derive the same Ed25519 identity from the key
(HKDF) and pin the other's public key, so the handshake completes only if both
sides hold the key. An on-path attacker can neither read the traffic nor
impersonate either party — no certificate files, no CA, no first-use trust
leap. The unary HMAC layer stays on top (client auth + replay guard); mutual
TLS is what additionally authenticates the client on the session path below.

Session side-channels (terminals, file transfer) run over bierpc's
**persistent call** on this same connection, not a separate token'd port
(`protocol::session`). Because the connection is mutually authenticated, a
session carries no HMAC of its own; the server validates and replies with
`Result<SessionStart, ApiError>` before any bytes flow. Terminals frame both
directions and end with an explicit `term::Close` handshake, since the shared
connection is reused for the call's reply and so can never be closed to mean
"done"; transfers self-delimit with a length prefix and take the reply as their
commit ack.

Rotating a key (`server keygen`) locks out every client still holding the old
one, by design.
